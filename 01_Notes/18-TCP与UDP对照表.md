## 一、五行对照表

| | TCP | UDP |
|---|---|---|
| **连接** | 先三次握手建立连接，再发数据 | 不建连接，直接发 |
| **可靠** | 丢包能发现，会重传 | 不管丢没丢，发出去就不负责 |
| **有序** | 每个字节有序号，乱序到达也能按号重排 | 没有序号，先到先交 |
| **速度** | 要等确认、要重传，慢 | 无连接无确认，开销小，快 |
| **场景** | 网页、文件下载、SSH、邮件 | DNS 查询、直播、在线游戏、视频通话 |

## 二、逐行解释

### 1. 连接

**硬核**：TCP 传输数据前要先完成三次握手（SYN → SYN+ACK → ACK），双方确认收发能力后才开始传；结束后要四次挥手。UDP 没有握手，构造好报文直接交给 IP 层发出去。

💬 **大白话**：TCP 是打电话，先“喂，能听见吗”确认两遍再说话；UDP 是往对方信箱塞纸条，塞完就走，不管他在不在家。

### 2. 可靠

**硬核**：TCP 给每个字节编号，接收方回 ACK 确认；超时没收到确认就重传。UDP 没有 ACK、没有重传，丢了就是丢了，协议层不告诉你。

💬 **大白话**：TCP 是快递要签收，没签收就再送一次；UDP 是撒传单，风刮走几张也没人管。

### 3. 有序

**硬核**：TCP 的序号让接收方能把乱序到达的报文段重新排好，再交给应用层。UDP 没有序号，网络先送到哪个就交哪个，顺序由应用自己处理。

💬 **大白话**：TCP 收快递会按单号排队；UDP 是一把信倒桌上，谁先到谁在上面。

### 4. 速度

**硬核**：TCP 慢在三处——建连要一个 RTT、每个数据段要等确认、丢了要重传；它还有流量控制（怕对方收不下）和拥塞控制（怕网络堵）——这两套机制单独写在 [19 号](19-TCP的可靠传输机制.md)。UDP 没有这些，头部只有 8 字节，发出去就不管。

💬 **大白话**：TCP 像挂号排队，一步一确认，稳但慢；UDP 像扔纸飞机，快，但可能半路掉。

> 注意：不是“TCP 天生慢”。**是它为了保证不丢不乱，多花了这些成本。** 网络好的时候两者差距不大。

### 5. 场景

**硬核**：
- 网页、文件、邮件、SSH → 少一个字节内容就坏了，**必须可靠** → TCP
- DNS 查询、直播、游戏、视频通话 → 数据小、要快、丢一点能忍（重发反而更卡）→ UDP

💬 **大白话**：传合同用挂号信（TCP），喊一嗓子“开饭了”用嗓子（UDP）——喊漏了再喊一遍就行。

## 三、头部结构：8 字节 vs 20 字节起

这是“UDP 开销小”最直接的证据。

**UDP 首部（固定 8 字节，没有选项）**

| 字段 | 长度 | 作用 |
|---|---|---|
| 源端口 | 2 字节 | 谁发的 |
| 目的端口 | 2 字节 | 发给谁 |
| 长度 | 2 字节 | 整个数据报多长 |
| 校验和 | 2 字节 | 可选的差错检测 |

**TCP 首部（20 字节起，带选项可到 60 字节）**

| 字段 | 作用 |
|---|---|
| 源/目的端口 | 各 2 字节 |
| **序号 Seq** | 我发到第几个字节 |
| **确认号 Ack** | 我期望你下一个发第几个 |
| 数据偏移 | 首部有多长 |
| **标志位** | SYN / ACK / FIN / RST / PSH / URG |
| **窗口** | 我还能收多少（流量控制） |
| 校验和 | 差错检测 |
| 紧急指针 | 少用 |
| 选项 | MSS、SACK、时间戳、窗口缩放 |

💬 **大白话**：UDP 的信封上只写“谁寄、寄给谁、多厚”；TCP 的信封上还要写“这是第几页、我要第几页、我还能收几页、这封是不是急件”。

**所以：UDP 省下的不是“技术”，是“信息”。** 没有序号就没有重排，没有窗口就没有流量控制。

## 四、怎么选：一张决策图

```
能容忍丢包吗？
├─ 不能（文件、网页、登录、支付） → TCP
└─ 能（直播、语音、游戏位置同步）
     └─ 要求低延迟吗？
          ├─ 要 → UDP
          └─ 不要 → TCP 也行（省事）
```

**常见应用层协议选型**

| 协议 | 传输层 | 为什么 |
|---|---|---|
| HTTP/1.1、HTTP/2 | TCP | 内容不能缺字节 |
| **HTTP/3（QUIC）** | **UDP 443** | 自己要可靠，但不想被 TCP 的队头阻塞拖住 |
| DNS | UDP 53（大响应/区域传送用 TCP） | 一问一答，小包快 |
| DHCP | UDP 67/68 | 客户端还没 IP，没法建 TCP |
| NTP | UDP 123 | 时间同步，丢一次下次再对 |
| SNMP | UDP 161 | 轮询设备状态，丢一次无所谓 |
| Syslog | UDP 514 | 日志，丢几条能接受 |
| SSH | TCP 22 | 交互式会话，不能乱序 |
| RDP | TCP 3389 | 同上 |

💬 **大白话**：要“一个字都不能少”的走 TCP；要“快、丢了再喊一遍”的走 UDP。

## 五、抓包怎么区分（实操）

| 现象 | 说明 |
|---|---|
| Wireshark 里 Protocol 列显示 `UDP` | UDP 报文，没有握手、没有 ACK |
| 同一个五元组只有一问一答两行 | 典型 DNS（UDP 53） |
| `tcp.flags.syn==1` 抓不到它 | UDP 没有标志位 |
| 看到 `UDP 443` | 大概率是 **QUIC / HTTP/3** |
| 大量 `UDP` 包、源 IP 分散、无后续 | 可能 UDP Flood / 反射放大 |

**过滤命令**

```
udp                只看 UDP
udp.port==53       只看 DNS
tcp.flags.syn==1   只看 TCP 握手（UDP 永远不会出现）
```

💬 **大白话**：TCP 的包有“开场白和确认信”，UDP 的包是“裸奔的一张纸”。

## 六、面试常追问（5 条）

**① TCP 为什么会“粘包”？**
TCP 是**字节流**，没有消息边界；应用层要自己定长度（定长/分隔符/长度前缀）。

**② UDP 也能做可靠传输吗？**
能，但要自己实现：序号、ACK、重传、拥塞控制——**QUIC 就是这么干的**，把可靠性搬到应用层，绕开 TCP 的队头阻塞。

**③ 为什么 DNS 用 UDP，响应大了怎么办？**
小包一问一答快；响应超过 512 字节（或 `TC=1`）或区域传送时，**改用 TCP 53**。

**④ UDP 有校验和，为什么还说“不可靠”？**
校验和只能发现“这一包坏了”，**发现后直接丢弃，不负责重传**。

**⑤ 视频通话为什么不用 TCP？**
TCP 丢包重传会引入延迟和队头阻塞，**实时场景宁可丢帧也不要等**。

---

## 七、两个容易混的点（再强调）

**① “可靠” ≠ “有序”**
可靠是**丢了能不能补**；有序是**到了能不能排整齐**。两件事，TCP 都做，UDP 都不做。

**② “UDP 快”不是因为它更高级**
是因为它**少做了事**。要可靠又要快，就得在应用层自己补。
